# 第一题 — 简答部分

## 问题 1: 你是如何设计 prompt 来确保 JSON 格式输出的? 正向约束和负向约束分别用了哪些?

### 整体设计思路

采用 **"System 强约束 + 输出格式锚点 + 代码侧兜底"** 三层策略,把"输出合法 JSON"
这件事从单纯依赖模型的指令跟随,变成一个工程上可保证的结果。

**(1) 把 JSON Schema 直接写进 system prompt。**
让模型在生成前就"看到"目标结构,包括字段名、类型、枚举值、示例值。比起描述性
要求 (例如"请输出 JSON,包含 date 和 factors 字段..."), 直接给 Schema 收敛速度更快,
字段大小写、嵌套层级几乎不会出错。

**(2) 强制输出格式锚点。**
要求模型用 ```` ```json ... ``` ```` 代码块包裹回复,代码侧用正则
`r"```(?:json)?\s*(\{.*\})\s*```"` 抠出纯 JSON,避免任何前后解释性文字干扰
`json.loads`。

**(3) 调参与兜底。**
- `temperature=0` 关闭随机性, 保证可复现。
- `max_tokens=2048` 给足空间, 防止 JSON 被截断造成不闭合。
- 若 `json.loads` 抛 `JSONDecodeError`, 自动把上一轮的错输出和异常信息回传给模型,
  让它输出"修正版", 只重试一次, 避免死循环。

### 正向约束 (Positive Constraints) — 告诉模型"必须怎么做"

| #   | 约束                                                              | 目的                                |
| --- | ----------------------------------------------------------------- | ----------------------------------- |
| 1   | 只输出一个 JSON 对象,用 ```json``` 代码块包裹                     | 便于正则提取,杜绝多余文字           |
| 2   | 字符串使用双引号,中文字段保持中文                                 | 保证 `json.loads` 不报错             |
| 3   | 日期统一 ISO 格式 (`YYYY-MM-DD` 或 `YYYYMMDD`)                    | 便于后续时间序列对齐                 |
| 4   | 数值字段为数字类型,单位通过字段名表达 (`change_bp`, `close` 等)   | 下游可直接做数值运算                 |
| 5   | `factors` 数组按事件在原文中出现的先后顺序排列                    | 方便人工 diff/校对                   |
| 6   | 每张因子卡必须包含 `source_quote`,从原文摘录                      | 可追溯, 抑制幻觉                     |
| 7   | `sentiment_score ∈ [-1, 1]`, 保留一位小数                         | 数值规整, 便于聚合统计               |
| 8   | `cross_asset_summary` 中无数据的子项保留空对象 `{}`               | Schema 稳定, 下游键访问不会 KeyError |

### 负向约束 (Negative Constraints) — 告诉模型"不准做什么"

| #   | 约束                                                                 | 目的                            |
| --- | -------------------------------------------------------------------- | ------------------------------- |
| 1   | 禁止输出 Schema 以外的字段; 禁止改字段名大小写                       | 锁死 Schema                     |
| 2   | 禁止编造原文未出现的数字、机构、日期、言论                           | 抑制幻觉, 与第 6 条正向约束配合 |
| 3   | 禁止把多个事件合并到同一张因子卡 (一事一卡)                          | 保持事件原子性, 便于聚合         |
| 4   | 禁止使用 `null` / `None` / `NaN`; 缺失数值不出键, 缺失字符串用 `""` | 消除跨语言 null 语义差异          |
| 5   | 禁止在 JSON 中加入注释 (`//` 或 `/* */`)                             | 保证标准 JSON 可解析             |
| 6   | 禁止使用 markdown 标题/列表/加粗等格式                              | 防止污染输出                     |
| 7   | 禁止把单位写进数值 (`"4.28%"` → `4.28`; `"12bp"` → `-12`)            | 数值字段保持纯数字               |

### 这套约束的关键洞察

- **正向约束负责"长什么样"**,把 Schema 锁死;
- **负向约束负责"不要长歪"**,提前堵住模型最容易犯的几个错(幻觉、合并事件、加注释、把单位写进数字);
- 两者必须**配对使用**: 例如"必须有 `source_quote`" (正向) 与 "禁止编造原文未出现内容" (负向)
  组合起来,模型一旦要写引语就会回到原文确认数值,显著降低数字编造概率。

## 问题 2: 简单说明你本次笔试使用的大模型 / AI 工具,以及使用经验

### 使用的工具

- **大模型**: **Claude (Anthropic)**, 具体模型 `claude-opus-4-7` (1M 上下文版)。
  代码里也兼容切换到 `claude-sonnet-4-6` (速度更快、成本更低) 或
  `claude-haiku-4-5-20251001` (最便宜, 适合高频批处理), 可按精度/成本权衡。
- **调用方式**: 官方 `anthropic` Python SDK (v0.103.x), 标准 `client.messages.create`
  接口, system 与 user 分开传, `temperature=0`。
- **开发环境**: Claude Code (Anthropic 官方 CLI), 在云端开发容器里完成代码编写、
  prompt 调试与运行日志记录, 通过 git 提交到指定分支。

### 使用经验

1. **指令跟随能力强,但仍需"显式 Schema"**
   描述性要求 (例如 "返回包含 date 和 factors 的 JSON") 在简单场景能用,
   但只要字段超过 5 个或存在嵌套,就必须把完整 Schema(含字段注释/枚举值/示例值)
   写到 system 里, 否则会出现字段名小写化、漏字段、枚举值自创等情况。

2. **`temperature=0` + 显式锚点 = 工程可用**
   只要把输出格式锚定到 ```` ```json ... ``` ```` 代码块, 配合 `temperature=0`,
   同一输入几乎 100% 复现同一输出, 满足金融场景对可重复性的要求。

3. **抑制幻觉的最有效手段是"原文锚定"**
   单纯写 "禁止编造" 收效一般; 改成正向要求每个事件都必须给出 `source_quote`,
   等于强迫模型在生成数值前先回到原文确认一遍, 数字编造率显著下降。

4. **代码侧兜底是底线**
   即便模型已经很稳, 仍建议保留 "正则抠 JSON + `json.loads` 失败自修复" 两层兜底。
   生产环境跑量大时, 偶发的代码块外多写一句话、或截断不闭合, 都能被这两层兜住。

5. **中文金融文本上 Claude 表现稳健**
   对央行术语 (鹰派/鸽派/降准)、单位换算 (bp、万亿、个百分点)、
   日期表达 (中文年月日 → ISO) 的理解准确, 极少出现错译或类别错位。

6. **关于 Claude Code 这个工具本身**
   写本题时,代码、prompt 设计文档、运行日志、自我修复逻辑都在 Claude Code 里一气呵成,
   它的好处是: 模型能直接读写仓库文件、跑命令、看到 `pip` 装包失败的真实报错并自动重试,
   比"在网页上让模型生成代码再手动粘贴"的迭代效率高一个数量级,
   是这次笔试里"实际写代码"环节的主要生产力工具。
